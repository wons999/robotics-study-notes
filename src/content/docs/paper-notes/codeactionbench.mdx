## 한 줄 요약과 문제의식

agent가 RGB에서 metric geometry와 grasp/placement target을 추정해 Python policy로 실행할 때, **잘 쓰인 program, 도달한 TCP, 움직인 object, 완료된 task, 올바른 완료 선언은 서로 다른 성과**다. CodeActionBench는 이 경계를 숨겨진 물리 verifier와 단계별 분석으로 평가한다.

VLA는 dataset으로 observation→action policy를 학습한다. Code-as-Policy는 inference 중 robot API를 조합한 program을 만든다. 기존 code policy에는 object pose나 perception/grasp specialist가 주어지는 경우가 있는데, 이 benchmark는 agent가 직접 pixels·기하 가정·관측/접촉 feedback에서 spatial estimate를 구성하도록 한다.

| simulator·robot | SAPIEN / RoboTwin 2.0, ALOHA-AgileX dual-arm manipulation |

| RGB | head 640×480, wrist 320×240; observation ID와 calibration 제공 |

| 좌표 | world xyz는 m, x right·y forward·z up, quaternion **wxyz** |

fixed simulator seed는 model/provider sampling까지 같은 seed라는 뜻이 아니다. accepted attempt set은 documented infrastructure/superseded run을 제외하지만 agent error·runtime error·budget exhaustion은 실패로 남긴다. benchmark와 agent 사이의 gateway는 schema·budget을 검사하며, agent가 숨겨진 verifier를 query하는 tool은 없다.

## Method: RGB에서 target을 만들고 program으로 실행하기

### 관측·기하·motion API

총 robot tool 29개에 `run_code`, `done`을 더해 31개 tool이다. direct call도 가능하고 program의 loop/branch/function으로 조합할 수도 있다.

<PaperFigure src="/codeactionbench/table-04.png" alt="Table 4: state·camera·anonymous finger-contact API" caption="Table 4, p.16. state·camera·anonymous finger-contact API. PDF v1에서 추출." />
<PaperFigure src="/codeactionbench/table-05.png" alt="Table 5: agent-selected geometry와 pose construction API" caption="Table 5, p.17. agent-selected geometry와 pose construction API. PDF v1에서 추출." />

| tool family | 무엇을 제공하는가 | 무엇을 agent가 정하는가 |
| --- | --- | --- |
| state / camera | measured TCP·finger gap, RGB, intrinsics/extrinsics, capture-time wrist pose | 볼 camera·view·state query |
| ray / projection / plane intersection | calibrated ray와 agent-supplied plane의 교점, projection | pixel·plane·surface interpretation |
| motion-pair triangulation | wrist의 알려진 이동 전후 RGB와 camera displacement로 selected correspondence triangulation | 같은 point의 두 pixel correspondence |
| scale estimation | measured gripper separation 또는 object-size prior로 scale estimate | object extent·size prior·edge direction |
| grasp candidate / pose preview | supplied approach/opening axes에서 quaternion 후보, image overlay, candidate 비교 | 적절한 contact side·grasp direction·placement target |
| reachability | planner가 target path를 찾았는지 | target pose와 다음 행동 |

calibration과 geometry solver는 사용할 수 있지만 object pose를 자동으로 알려주는 oracle는 아니다. ray-plane 결과는 plane assumption에, size 결과는 prior에, triangulation은 pixel correspondence에 의존한다. numerical uncertainty 출력도 모든 pixel/calibration error를 포함하는 정확도 보증은 아니다.

<PaperFigure src="/codeactionbench/figure-07.png" alt="Figure 7: metric scale·selected pixels·pose preview·candidate 비교" caption="Figure 7, p.16. metric scale·selected pixels·pose preview·candidate 비교. PDF v1에서 추출." />
<PaperFigure src="/codeactionbench/table-07.png" alt="Table 7: bounded TCP motion·probe·gripper API와 measured feedback" caption="Table 7, p.18. bounded TCP motion·probe·gripper API와 measured feedback. PDF v1에서 추출." />

`reach_tcp`, `reach_both_tcp`, single/both `move_delta`, `probe_contact_along`, `set_gripper`가 motion을 만든다. contact probe는 제한된 거리·step size로 진행하고 contact 변화·measured TCP/finger pose·stopping reason을 반환한다. gripper normalized 값은 0=close·1=open이다. 실패하거나 멈춘 motion에서도 일부 physics가 진행될 수 있으므로 **achieved state를 다시 읽어야 한다**.

cuRobo의 robot self-collision check와 scene/world collision check는 별개다. benchmark configuration에서는 table/object world collision constraint를 제공하지 않으므로 reachable target이 contact-free path라는 뜻은 아니다. 이는 agent가 이미지와 feedback으로 환경을 고려해야 하는 조건이다.

<PaperFigure src="/codeactionbench/table-06.png" alt="Table 6: tool 사용 subset별 success; causal ablation 아님" caption="Table 6, p.18. tool 사용 subset별 success; causal ablation 아님. PDF v1에서 추출." />

Table 6은 해당 geometry/contact tool을 사용한 attempt subset의 success다. 예를 들어 Astra triangulation 55/75=73.3%, contact probe 5/6=83.3%지만 서로 다른 subset과 사용 선택이므로 “probe를 쓰면 83.3% 성공한다”는 causal ablation이 아니다. 여러 column에 같은 attempt가 중복 집계될 수 있다.

### Program runtime과 budget

`run_code`는 Python control flow, functions, `numpy`·`math` 계산으로 tool을 묶는다. 하나의 submitted program은 charged tool call 하나이며 내부 robot call은 call budget을 추가 소비하지 않는다. 그러나 모든 physical motion은 simulator time budget에 포함된다. 따라서 program으로 call budget을 절약해도 physical execution이 무제한인 것은 아니다.

program exception·recoverable action interruption은 feedback을 제공한다. interruption 뒤의 남은 call은 실행하지 않으며, 관측과 achieved state를 기준으로 복구한다. runtime은 허용된 API만 노출하고 scene GT는 parent 측에 남긴다. API 제한과 child-process isolation의 구현 확인은 완전한 security proof와 구분한다.

task별 reference solution은 evaluator의 budget feasibility를 확인하기 위한 것으로 agent에게 공개하지 않는다. estimated expert completion time을 t_expert_min(분), official demonstration의 simulation duration을 t_expert_sim(초)라 하면 아래 규칙이다. budget 산출 기준과 Table 3의 별도 reference-solution 자원 사용은 구분한다.

```text
B_tool = ceil(14 × t_expert_min)
B_sim  = ceil_to_5_seconds(max(60 seconds, 5 × t_expert_sim))
ceil_to_5_seconds rounds upward to the nearest multiple of five seconds
```

25 task의 call budget은 28–98, simulation budget은 60–175초다. inference 중의 wall time은 simulation budget과 다르다.

<PaperFigure src="/codeactionbench/table-03a.png" alt="Table 3a: task goal·seed·scoring·budget·reference feasibility, 앞부분" caption="Table 3a, p.14. task goal·seed·scoring·budget·reference feasibility, 앞부분. PDF v1에서 추출." />
<PaperFigure src="/codeactionbench/table-03b.png" alt="Table 3b: task goal·seed·scoring·budget·reference feasibility, 이어짐" caption="Table 3b, p.15. task goal·seed·scoring·budget·reference feasibility, 이어짐. PDF v1에서 추출." />

task family는 tool/contact 4, organization/assembly 11, dual-arm cooperation 4, handover/regrasp/reorientation 4, articulated-device 2다. Table 3의 instruction·seed·final/latch scoring·budget·reference resource를 함께 보면 쉬운 contact press와 object transport의 차이를 확인할 수 있다.

### Context와 agent harness

reference harness는 최근 두 observation round의 RGB 최대 6장을 유지하고, text에는 stable observation IDs를 남겨 예전 관측을 필요할 때 재조회한다. context limit 근처에서 최근 8 assistant/tool unit은 원문을 보존하고 이전 text는 고정 규칙으로 최대 128-entry ledger로 정리한다. model-generated summary를 사용하지 않으며 그래도 초과하면 종료한다.

reference model 7개에 Codex CLI/Astra와 Claude Code/Opus 구성을 더한다. Codex CLI 0.154.0은 built-in code/read-only 환경과 제한된 도구를 사용하고, Claude Code 2.1.212는 file/shell/web/delegation을 비활성화하며 tool search를 허용한다. 둘 다 같은 robot MCP API·resource·verifier 계약을 사용하지만 context·orchestration은 vendor harness가 맡는다.

<PaperFigure src="/codeactionbench/table-08.png" alt="Table 8: model ID·reasoning·output cap, vendor-managed 차이" caption="Table 8, p.19. model ID·reasoning·output cap, vendor-managed 차이. PDF v1에서 추출." />

reasoning은 대부분 high, Qwen은 medium이다. reference의 output token cap은 Astra vendor harness와 달리 명시되어 있으며 Grok 8,192, Gemini 65,536, Qwen/Kimi 131,072, 나머지 128,000이다. provider 간 같은 reasoning label이 같은 실제 token budget을 뜻하지 않는다. **Astra reference-harness row가 없으므로 Astra 모델과 Codex harness의 효과를 분리할 수 없다.**

## Dataset, Model Architecture와 Training Recipe

이는 training dataset 생성/학습 연구가 아니라 fixed evaluation suite다. sample은 task card·scene seed·embodiment·budget, observation ID·RGB/calibration/state, tool/program·execution feedback, hidden final verdict·event log·analysis annotations으로 구성된다. agent-visible record와 evaluation-only record를 분리한다.

VLM/LLM의 내부 architecture, parameter count, pretraining data·loss·optimizer·robot contamination은 benchmark에서 공개하지 않는다. task-specific gradient update나 learned action head는 없다. 따라서 학습 batch/LR/augmentation/checkpoint recipe는 해당하지 않는다. 재현 요소는 exact task instance, model identifier·reasoning/output cap, harness version/context rules, API schemas, execution backend, budget/verifier revision이다.

## Hidden verifier와 단계별 progress

21 task는 final-state 조건을, hammer·bell·stapler·bin pouring의 4 task는 필요한 physical event와 추가 final 조건을 사용한다. upstream environment의 과거 `success` latch만으로 최종 성공을 인정하지 않는다. laptop은 expert의 특정 arm 선택을 제거하되 angle/TCP 조건을 유지했고, shoes는 object identity를 바꿔 배치해도 조건을 만족하면 인정한다. roller는 양팔 contact, bread/skillet은 release·상대 geometry 조건을 보강한다. 따라서 원래 RoboTwin success score와 직접 비교하지 않는다.

Figure 9는 task success, 실패했지만 subgoal 도달, spatial checkpoint만 도달, 아무 checkpoint도 확인되지 않은 경우를 나눈다. Astra는 success 또는 checkpoint progress가 73/75, Opus Claude Code는 68/75, Opus Reference는 67/75다. 전체 491 failure는 subgoal 도달 89·spatial만 도달 230·아무 checkpoint도 확인되지 않은 경우 172로 나뉜다. TCP region에 도착했다는 사실과 object를 옮겼다는 사실을 구분해야 실패 원인을 좁힐 수 있다.

## Failure Analysis: 491회 실패의 최초 확인 가능한 단계

<PaperFigure src="/codeactionbench/figure-06.png" alt="Figure 6: 구성별 success와 earliest supported failure stage" caption="Figure 6, p.7. 구성별 success와 earliest supported failure stage. PDF v1에서 추출." />
<PaperFigure src="/codeactionbench/figure-10.png" alt="Figure 10: 491 failures의 stage·세부 physical trace 분해" caption="Figure 10, p.27. 491 failures의 stage·세부 physical trace 분해. PDF v1에서 추출." />

전체 675회 중 184회 성공·491회 실패다. 각 실패를 가장 이른 evidence-supported stage 하나에 할당한다.

| stage | 수 | 세부 유형 |
| --- | --- | --- |
| relevant region unconfirmed | 280 | compatible request 없음 225; compatible motion 실패 7; motion은 있으나 arrival 미확인 48 |
| object control unconfirmed | 77 | contact는 있으나 co-transport 없음 45; 도착 전 transport loss 2; TCP arrival이나 object transport 없음 30 |
| subgoal unmet / not maintained | 122 | arrival 후 release 없음 11; release했으나 goal 미완료 34; interaction region 도달 후 goal 미완료 47; 이전 subgoal 상실 30 |
| final gripper state only | 6 | 마지막 gripper 조건만 불충족 |
| mechanism unresolved | 6 | original/replay evidence 부족 |

Astra의 20 failure는 arrival-unconfirmed 8·object control 4·subgoal 8이다. 따라서 12/20=60%는 공간 도착 뒤의 stage다. Opus Reference도 23/38, Claude Code도 22/41이 late physical stage다. 반면 낮은 성능 구성은 region 도착 전 실패가 더 많다. “모든 실패가 perception 문제” 또는 “코드가 문법적으로 맞으면 성공”이라는 설명이 맞지 않는다.

object co-transport의 offline 기준에는 동일 object에 대한 finger contact, TCP와 object 각각 3cm 이상 이동, relative vector 변화 ≤3cm 등이 포함된다. agent에게 object identity를 주는 것이 아니라 분석기가 hidden state로 판정한다. 491 failure 중 481 replay·4 original-only·6 unresolved를 사용했다. model의 잘못된 target 요청이나 note를 physical trace보다 우선해 root cause로 단정하지 않는다. 단계 분류는 evidence description이며 단독 causal detector가 아니다.

<PaperFigure src="/codeactionbench/table-14.png" alt="Table 14: incomplete action의 planner/stall/deviation/allowance 분해" caption="Table 14, p.28. incomplete action의 planner/stall/deviation/allowance 분해. PDF v1에서 추출." />

Astra motion은 305/2,055=14.8%가 완주하지 못한다: planner refusal 187, stall 110, deviation 3, allowance stop 5. 전체 non-completed action 4,045개 중 2,783개는 physics를 진행했다. error 후 처음 state에서 다시 시작한다고 가정하면 누적 오차와 contact loss를 놓친다.

## Completion claim: 성공을 안다고 말할 수 있는가

<PaperFigure src="/codeactionbench/table-02.png" alt="Table 2: 75회 denominator와 success/failure별 correctness" caption="Table 2, p.8. 75회 denominator와 success/failure별 correctness. PDF v1에서 추출." />
<PaperFigure src="/codeactionbench/table-15.png" alt="Table 15: termination과 correct/over/under/absent claim 전체" caption="Table 15, p.28. termination과 correct/over/under/absent claim 전체. PDF v1에서 추출." />

`done`의 Boolean claim은 hidden verifier verdict와 별도다. Astra는 done 72/75, correct claim 68/75=90.7%다. 이는 **68회 task success가 아니라 성공/실패를 맞게 말한 총수**다. 실제 성공55회 중 correct success54·underclaim1이고, 실제 실패20회 중 correct failure14·overclaim3·absent3이다. failure에 대한 overclaim은 3/20=15%다.

Opus Reference는 done63·correct50, Claude Code는 done54·correct42다. 실패에서 correct claim은 각각 14/38·12/41로 낮다. Sonnet은 70/75가 explicit Boolean claim을 남기지 않았으며 69회 tool budget 종료와 Boolean 없는 done 1회가 포함된다. absent claim은 실패를 올바르게 인지한 claim이 아니다. 전체 failed attempt의 345/491=70.3%가 explicit claim을 남기지 않는다.

## Appendix Notes와 Code-Level Check

Appendix A는 task·seed·budget·scoring, B는 API와 spatial feedback, C는 harness/context/model 설정, D는 outcome/resource, E는 checkpoint, F는 failure analysis, G는 incomplete action·claim, H는 AI writing disclosure다. figure/table의 전체 내용은 아래 inventory와 해당 절에서 확인할 수 있다.

| 공식 source 경로 | 확인한 역할 |
| --- | --- |
| `src/codeaction/runtime/sandbox.py` | persistent child namespace에서 program 실행, 제한된 imports/AST/API; parent scene state와 public RPC를 분리. timeout/death/abort 뒤 namespace reset |
| `runtime/episode.py` | episode lifecycle, budgets, agent termination과 outcome 기록 |
| `verification/verifiers.py` | final check와 required event latch를 별도 적용; latch 누락을 fail closed 처리. analysis milestone이 agent tool이 아님 |
| `interface/tools/vision.py` | observation snapshot calibration으로 projection/ray/geometry 계산, agent-selected pixels 사용 |
| `backends/robotwin/scale.py` | public triangulation API의 two-ray midpoint, declared pixel perturbation·ray-gap uncertainty. calibration·correspondence 선택·scene change 오차는 제외 |
| `backends/robotwin/world.py`, `planner.py` | cuRobo planning과 world-collision configuration의 경계; world constraint와 self-collision을 구분 |
| `agents/reference/context.py` | observation retention·recent-unit/ledger compaction 정책 |

code revision을 기록한 이유는 현재 interface/context version과 논문의 exact harness version이 같다는 보장이 없기 때문이다. public source를 읽어 module 경계를 확인했으며 model weights/loss/training corpus는 이 repository에서 검증할 수 없다. simulator·provider API를 직접 실행한 재현 결과는 포함하지 않는다.

## 한계와 Citation Trail

25 fixed instances·3 stochastic attempts, 한 simulated robot/scene regime, no real-world transfer, model과 harness의 confounding, 제한된 output budgets, closed-model contamination과 pricing/accounting이 범위의 한계다. 실제 object 다양성이나 새 scene 일반화를 보여주는 대규모 train/test evaluation은 아니다. missing claim과 unresolved evidence도 숨기지 않고 따로 읽어야 한다.

Code as Policies·CaP-X·VLCP·OpenETA는 code control과 perception/privileged-input 경계를 비교하는 배경이다. [Unexpected Robot Policy](../unexpected-robot-policy/)는 calibration 없는 RGB/EEF direct target 평가이고, [GPT-Policy](../gpt-policy/)는 historical demo/action reference를 허용하는 real setting이다. [Astra embodied-policy 평가](../astra-embodied-policy-capabilities/)는 learned policy/controller와 Hybrid 협력을 포함한다. 같은 이름의 모델이라도 success denominator와 API가 달라 네 논문의 성공률을 한 leaderboard로 합치지 않는다.
